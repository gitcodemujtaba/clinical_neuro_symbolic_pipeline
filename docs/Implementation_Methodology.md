# docs/Implementation_Methodology.md

## Objective
* The central claim under test is that a neuro-symbolic pipeline combining zero-shot extraction, KG-grounded normalization, and LLM-based validation with a human-in-the-loop (HITL) active learning loop can match or exceed the performance of a pretrained generative baseline (Clinical-T5) on clinical entity/relation extraction from MIMIC-IV discharge notes[cite: 7].
* This approach aims to require substantially less human annotation effort over time as the system's knowledge base grows[cite: 7]. 
* Performance is evaluated on two distinct axes: concept-level accuracy against a gold standard, and effort reduction[cite: 7].

## Data Sources
* **MIMIC-IV-Note:** The primary input corpus consisting of structured discharge summaries[cite: 7]. Used two ways that must stay separated: (a) the bulk, unannotated corpus that drives the Stage 5 Active Learning stream, and (b) the 272-note gold-annotated evaluation subset below, which is explicitly excluded from (a) to prevent train/eval contamination.
* **imantsm/medical_abbreviations:** A static abbreviation to expansion dictionary split across 17 CSV files[cite: 7].
* **Athena/OHDSI OMOP:** Vocabulary tables ingested into DuckDB[cite: 7].
* **SNOMED CT US:** A parent-child (IS_A) subsumption hierarchy knowledge graph queried via Memgraph[cite: 7].
* **Guideline-derived triplets:** Triples curated from clinical guidelines (KDIGO, AHA/ACC, GOLD, SSC, NPSG/ESI) stored in the same graph as the SNOMED hierarchy[cite: 7].

### Evaluation Dataset — Confirmed (2026-08-07)
The PhysioNet **SNOMED CT Entity Linking Challenge v1.2.0** archive (the completed challenge, not the currently-open rolling DrivenData Benchmark — see `Proposal_Alignment_Review.md` §3.8 for the distinction between the two) is now present locally at `evaluaiton-dataset/snomed-ct-entity-linking-challenge-1.2.0/`. Verified directly against the files:

* `train_notes.csv` — 272 unique discharge notes, 2,374–24,858 characters each (mean ~10,257 chars). Columns: `note_id`, `text`.
* `train_annotations.csv` — 75,491 annotation rows across those 272 notes, 6,595 distinct SNOMED `concept_id`s. Columns: `annotation_id`, `note_id`, `start`, `end`, `span`, `concept_id`, `annotation_type`.
* **The official train/test split is preserved via the `annotation_type` column** — `train` (51,295 annotations / 204 notes) and `test` (23,131 annotations / 68 notes), disjoint at the note level (204 + 68 = 272). This matches the ~200/~70 split already assumed in `Evaluation_Criteria.md`, and — unlike the live rolling Benchmark, whose hidden test labels are not downloadable — **this archive ships the test-set gold concept IDs directly**, so a genuine held-out evaluation against the original official split is possible without needing to carve out a custom split or submit code to DrivenData's platform.
* A third `annotation_type` value, **`proposed_ACCEPTED`** (1,065 annotations / 233 notes, overlapping both train- and test-tagged notes), appears to be supplementary community-proposed labels accepted post-challenge. Decide explicitly whether to fold these into scoring or keep them out for fidelity to the original challenge split — recommend keeping them separate and reporting both ways rather than silently merging.
* **Medication coverage is broader than the live Benchmark's stated scope suggested.** A keyword scan of `span` text turned up 96+ drug-related annotations (`Aspirin`, `Warfarin`, `heparin drip`, `insulin regimen`, `oral antibiotics`, etc.) with real `concept_id`s. These are very likely SNOMED **Clinical Finding**-hierarchy concepts (e.g., "taking warfarin" as a finding) rather than **Substance**-hierarchy drug-product concepts, which would reconcile this with the live Benchmark's "substances/medications out of scope" rule — but this needs verifying against the loaded SNOMED KG once it's populated (check the FSN/domain of concept_ids like `722045009`, `281789004`). Don't assume the `Medication` GLiNER label is entirely unscoreable against this dataset until that's checked — it may be scoreable if mapped to the finding/therapy concept rather than the raw drug substance.
* **Known integration gotchas:** `start`/`end` are stored as floats (`"180.0"`), not ints — cast with `int(float(x))` before using them to slice `note.text`, or slicing will raise a `TypeError`. Also, the existing smoke-test scripts (`test_extraction.py`, `test_pipeline_e2e.py`, `test_preprocessing.py`) point `NOTES_PATH` at `data/raw_notes/discharge.csv`, which is a placeholder for the bulk unannotated MIMIC-IV-Note stream, not this evaluation set — the forthcoming `evaluation/eval_suite.py` needs its own loader pointed at `evaluaiton-dataset/snomed-ct-entity-linking-challenge-1.2.0/`, kept distinct from the AL-stream ingestion path.

## Pipeline Architecture
* **Stage 1 (Preprocessing):** scispaCy tokenizes the note, and known short forms are expanded using a word-boundary dictionary lookup before semantic processing occurs[cite: 7]. Character-offset mapping is tracked through this step so spans identified in the expanded text can be traced back to the original note[cite: 7].
* **Stage 2a (Extraction):** GLiNER performs zero-shot span extraction on the expanded text. *(Updated 2026-08-07: relation extraction was originally planned via Clinical-T5, but Clinical-T5 was removed from the live pipeline because it was pretrained on MIMIC-III/IV, creating a data-contamination risk against the evaluation notes — it is now used exclusively as an external baseline, see Baseline Comparison below. This leaves Stage 2a relation extraction unowned; a replacement approach — e.g. a relation-extraction-capable GLiNER variant, or an explicit decision to descope relation triples from the MVP — needs to be chosen. See `Implementation_Checklist.md`.)*
* **Stage 2b (Grounding & Normalization):** SapBERT converts extracted spans into dense vectors, and DuckDB resolves them to an OMOP concept ID via a tiered lookup (exact concept name, exact synonym name, then vector similarity fallback)[cite: 7]. A global similarity threshold of 0.72 gates whether a vector match counts as resolved[cite: 7].
* **Stage 3 (MoLLM Confidence-Gated Validation):** An ensemble of MedGemma 4B and OpenBioLLM 8B routes extractions based on Stage 2 confidence[cite: 7]. High-confidence inputs undergo a guideline-contradiction check, while low-confidence inputs prompt a deeper resolution attempt using provenance, the SNOMED hierarchy, and guideline-triplet evidence[cite: 7].
* **Stage 4 (Routing & Ingestion):** Accepted triples are tagged with their provenance path as AUTO_VALIDATED, MOLLM_RESOLVED, or HUMAN_VERIFIED[cite: 7]. Patient-instance facts are stored as `:PatientObservation` nodes linked via `:INSTANCE_OF` to `:Concept` nodes, keeping patient data structurally distinct from the reference ontology[cite: 7].
* **Stage 5 (Active Learning Feedback Loop):** The dynamic, hospital-specific knowledge graph (KG 3) feeds back into GLiNER's prompt and search space over time[cite: 7]. Updates are checked against a held-out gold-evaluation set to catch regressions[cite: 7].

## Baseline Comparison
* Clinical-T5 is utilized as an independent parallel baseline run separately on the same notes[cite: 7].
* Clinical-T5's generated output passes through the same SapBERT and DuckDB grounding step as the main pipeline to ensure both are scored at the concept-ID level rather than on raw text overlap[cite: 7].
* Comparisons happen at three longitudinal checkpoints: KG 3 empty (T0), roughly half of MIMIC-IV processed (T1), and fully processed (T2)[cite: 7].
