# MoLLM (Stage 3) Redesign — Proposal Informed by Qi et al. 2026 (MoLLIA)

**Date:** 2026-08-11
**Status:** implemented locally (S1-S9's core mechanisms + S10's Channel E), verified via py_compile and stub tests, NOT yet synced to EC2. See S11 for exactly what changed, where, and what's still open.
**Trigger:** direct request to review "Next Generation Active Learning: Mixture of LLMs in the Loop" (Qi et al., arXiv:2601.15773, AAAI 2026) and propose a Stage 3 redesign.
**Scope note:** this paper is not an outside suggestion — it is already **Reference [8]** in the project proposal's own Background Research section, cited as the direct intellectual precedent for this project's "Mixture of LLMs" framing. This document checks a specific, load-bearing claim: does the *actual mechanism* described in that paper match what Stage 3 currently does, and if not, which parts of it are worth adopting.

---

## 1. Verdict up front

**Partial adoption, not a rewrite.** MoLLIA solves a different-shaped problem than Stage 3 does, and forcing a literal port would itself be a proposal-alignment problem — it would pull effort into building infrastructure (an iteratively-retrained downstream classifier) that Objective 3 describes but Stage 4/5 haven't reached yet, at the expense of finishing the objective that's actually in flight. But one specific mechanism inside MoLLIA — replacing hand-tuned threshold arithmetic over ensemble outputs with a small **trained** meta-model — is a precise, currently-unimplemented fix for a problem this project has already measured and documented: `docs/Stage3_Open_Issues.md` Issue 4 found `composite_confidence` has **ECE = 0.7529** and is flat across correct and incorrect verdicts (all 6 gradable decisions landed in `[0.9, 1.0)` confidence against 16.7% actual accuracy). That is close to the exact failure mode MoLLIA's Table 2 was built to fix — hand-combined ensemble signals (vote-based, logits-based) underperform a **trained** aggregator (MoLAM) by a wide margin on every one of their four benchmarks.

Three of MoLLIA's four mechanisms decompose cleanly onto Stage 3's existing, already-logged data with no new instrumentation. One does not fit at all given what's built today. Details below.

## 2. What MoLLIA actually does (so the mapping is precise, not vibes-based)

Read directly from the paper, not summarized from the proposal's one-paragraph gloss:

- **Task shape:** closed-set multi-class classification (K ∈ {2,4,5,6} depending on dataset — AG News/IMDB/TREC/PubMed). Not an open-candidate resolution task.
- **MoLAM** (the actual annotation model): each of 5 LLMs (Gemma-2-9B, Llama-3.1-8B, Mistral-7B, Qwen2.5-7B, Yi-1.5-9B) is queried **T times** per input, producing a logits vector `z_i ∈ R^K` and a consistency vector `c_i ∈ R^K` (how often each class was predicted across T samples). These `2N·K` numbers are stacked into one feature vector and fed to a **trained XGBoost classifier** — trained on only 50 labeled examples plus pseudo-labeled unlabeled data above a confidence floor `σ=0.9`. MoLAM's output is what gets used, not the raw votes.
- **Negative labels** `y⁻`: classes every LLM assigns confidence below `δ=0.001` to. Used later as a penalty target, not thrown away.
- **Annotation discrepancy** `d_anno`: a **separate**, task-specific small classifier (the actual "AL model" being trained across rounds — DistilBERT/DistilRoBERTa) predicts a label; if it disagrees with MoLAM's label, that disagreement is used to **down-weight** that example in the AL model's next training step (`α=0.5`). The paper's own ablation (Fig. 6) shows this discrepancy signal beats entropy, margin, and consistency-based uncertainty at flagging wrong labels — 0.8574 detection rate vs. ~0.83 for the next-best method.
- **Negative learning loss**: penalizes the AL model for putting probability mass on `y⁻`.
- **The active learning loop**: every round, the (possibly wrong) MoLAM label is added to the labeled pool, the AL model is retrained from a cold start, and the next batch of uncertain points is queried. This loop is the entire point of the paper — MoLAM's output only matters because it becomes training signal for a model that gets evaluated at the end.

That last point is the one to hold onto: **MoLLIA is a labeling engine for training a downstream classifier.** Everything else (negative labels, discrepancy, the loop) exists in service of that downstream model's accuracy.

## 3. Where the task shapes diverge — and why that matters

| | MoLLIA | Stage 3 (current) |
|---|---|---|
| Output space | Fixed K classes, same K every call | Variable — up to 3 candidates (LOW tier) or a 3-verdict contradiction check (HIGH tier); `RESOLVED_TO_CANDIDATE_N`'s N is per-record |
| Downstream consumer of the label | A retrained classifier (DistilBERT), evaluated every AL round | `mollm_decisions` → (eventually) Stage 4 KG3 write-back. No retrained classifier exists in this pipeline. |
| Per-model sampling | T repeated generations per LLM (self-consistency) | 1 generation per LLM (2 models, single T4 GPU, guided JSON decoding) |
| Grounding | None — MoLAM is unaware of any external evidence, purely a function of LLM outputs | KG-grounded: retrieval, citation verification, assertion gating — this **is** Objective 2 |
| What decides "trust this" | A trained classifier over stacked LLM outputs | Three hard-coded safety rules, then a hand-tuned threshold on mean logprob |

Two of these are not stylistic differences, they're reasons a literal port would be wrong for this project specifically:

1. **No downstream trainable classifier exists yet.** `docs/Proposal_Alignment_Review.md` already flags Stage 4/5 as unimplemented. `d_anno` and the negative-learning loss are both defined *in terms of* that classifier's predictions and training loss. Building one just to have something to compute `d_anno` against would be scope creep in the wrong direction — Objective 3's HITL routing and KG write-back haven't landed yet, and that's the actual next objective, not a parallel classifier-training track MoLLIA happens to need.
2. **T-fold self-consistency collides with a documented hardware constraint, not a soft preference.** `scripts/start_vllm.sh`'s header records that both ensemble members already run at disjoint, tightly-budgeted `--gpu-memory-utilization` fractions (0.40/0.55) on a single Tesla T4, sequential startup required or the KV-cache allocation races. `docs/Stage3_Open_Issues.md` measured throughput at 5.32s/record median for T=1. T=5 (matching the paper's setup) would not just be 5x slower — vLLM's KV cache budget was sized for one in-flight sequence per model at this `--max-model-len`, so T>1 concurrent samples may not even fit without lowering `--max-model-len` further, degrading the already-tight 8,192-token OpenBioLLM budget documented in `docs/MoLLM_Stage3_Retrieval_Design.md` §6.5.

So: no wholesale MoLLIA port. What follows is what survives contact with the actual constraints.

## 4. What to adopt — three mechanisms, mapped to exact current code

### 4.1 Replace `route()`'s hand-tuned threshold with a trained calibrator (the core recommendation)

**Current state** (`src/mollm_ensemble.py:552-629`): `combine()` produces `composite_confidence` as a mean of two logprob-derived numbers, optionally penalized if they spread too far apart. `route()` then compares this single scalar against two hand-picked constants, `AUTO_VALIDATE_THRESHOLD = 0.85` and `MOLLM_RESOLVE_THRESHOLD = 0.60` (line 64-65). This is architecturally the "logits-based ensemble" baseline in MoLLIA's own Table 2 — averaging raw per-model signals — which the paper's own experiments show is consistently beaten by a trained aggregator (MoLAM) on every one of four benchmarks, sometimes by double digits (e.g., PubMed: logits-based 0.6802 vs. MoLAM 0.7772).

This project has already independently measured that this style of aggregation doesn't work here either: Issue 4's ECE of 0.7529 and the flat `[0.9,1.0)` confidence band regardless of correctness is the same failure the paper's Table 2 documents in a different domain.

**Proposal:** train a small classifier — call it **`MoLLM-Cal`** — that takes the ensemble's *already-logged* per-record features and outputs `P(this decision is correct)`, replacing the two magic-number thresholds. This is MoLAM's core idea (stacked LLM output features → trained classifier), scoped down to what fits the data volume this project will actually have.

**Feature vector — nothing here requires new instrumentation.** Every field below already exists in `mollm_decisions` (`store_decision()`, `src/mollm_ensemble.py:876-900`):

- Per model (from `models JSON`, populated by `_query_one()`): `verdict`, `logprob_confidence`, `raw_confidence_label`, `decoding_mode`, `verdict_out_of_vocabulary` (bool)
- `ensemble_agreement`, `composite_confidence`, `confidence_spread` (from `combine()`)
- `citation_verified`, count of `citation_checks` entries and how many failed
- `confidence_tier_in` (HIGH/LOW), `mode` (contradiction/resolution)
- From `retrieved_context JSON`: number of rules retrieved, max `match_confidence`, whether Channel D (weak, semantic-only) fired vs. A/B (code-based)
- Stage 2b's own signal (join to `normalized_entities`, not currently fed into Stage 3 at all — see §4.2)

**Label:** exactly what `evaluation/cal_eval.py` already computes for the gradable subset (resolution-mode, agreeing, crosswalked against DrivenData gold SNOMED). This is the same join `cal_eval.py`'s `load_gradable_decisions()` already performs — the training set assembly is close to free.

**Model choice:** MoLAM uses XGBoost on 50 labeled examples. Given this project's gradable sample is currently in single digits (n=6 in the last measured run) and will grow slowly as the batch run progresses, **start with logistic regression or a depth-2 decision tree, not XGBoost** — fewer parameters than examples is a real risk at n<100, and a linear model over ~8-10 features is both less prone to overfitting and easier to defend in a viva ("here is the coefficient on citation_verified") than a boosted ensemble whose behavior on 6-50 training points is hard to reason about. Revisit XGBoost once the batch run and subsequent runs push the gradable sample past a few hundred.

**Critically — this replaces the threshold comparison only, never the three safety rules.** `route()`'s three hard gates (disagreement → HITL, citation failure → HITL, CONTRADICTED/INSUFFICIENT_EVIDENCE/NONE_CORRECT → HITL) stay exactly as they are and run **before** MoLLM-Cal is even consulted. Issue 3's own finding — the `spirnolactone`/SPIRAPRILAT case, where composite_confidence (0.916) and ensemble_agreement (True) were both wrong and only `citation_verified=False` caught it — is direct evidence for this ordering, and MoLLIA's own paper structure agrees: negative learning and discrepancy in MoLLIA *augment* the base classifier's loss, they don't gate around a hard rule the way this project's safety rules do. A learned confidence score is strictly less trustworthy than a symbolic check when the two conflict, and nothing about training MoLLM-Cal changes that ordering.

### 4.2 Annotation discrepancy — free, and already flagged by the paper as the single best signal

MoLLIA's Fig. 6 result is worth taking seriously on its own terms: `d_anno` (disagreement between the trained AL model and MoLAM) beat every uncertainty-based method they tested (entropy, margin, consistency) at flagging bad labels — not by a little; **it was the top bar in the chart, ahead of both AL-side and LLM-side uncertainty metrics.** Their ablation (Fig. 7, Table 4) found dropping annotation discrepancy hurt performance more than dropping any other single ablated component except negative learning.

Stage 3 doesn't have a trained AL classifier to compute this against — but it has something structurally equivalent for free: **Stage 2b's deterministic normalization already produced an independent judgment** (`match_tier`, `similarity_score`, which candidate ranked first) before Stage 3 ever ran. That's not an LLM-in-the-loop signal, it's a symbolic one, which if anything is a *stronger* fit for this project's "white-box, deterministic, auditable" pitch than the paper's own SLM-based discrepancy — MoLLIA needed a trained neural network to produce the comparison point; this pipeline already has a rule-based one sitting right there, unused.

**Proposal:** compute `d_anno = I[MoLLM's resolved candidate ≠ Stage 2b's top-ranked candidate]` for resolution-mode decisions, and add it as a feature to MoLLM-Cal (§4.1) — cheap to compute (one join, already-available fields), directly motivated by the paper's own best-performing ablation, and costs nothing beyond a join because both sides of the comparison are already persisted (`normalized_entities.match_tier`/`candidates` and `mollm_decisions.models[].verdict`).

**Do not use it standalone as a fourth safety-rule gate.** It's a feature into the trained calibrator, not a hard rule, because — unlike model disagreement or citation failure, where the safety-rule framing has a clean, defensible clinical rationale ("two independent validators disagreeing is not something a threshold should paper over") — Stage 2b overriding Stage 3 or vice versa is *exactly the kind of case the resolution mode exists to adjudicate* (candidate 1 vs. candidate 2 vs. none-correct). Treating every override as an automatic HITL trip would defeat the purpose of the resolution mechanism; treating it as one input the calibrator learns to weight is the correct level of trust.

### 4.3 Negative-candidate bookkeeping — symbolic, not gradient-based

MoLLIA's negative labels (`y⁻`, classes every LLM assigns near-zero confidence) are used for a gradient-based penalty (`L_neg`) against the retrained classifier — not adoptable here for the reason in §3 (no such classifier). But the underlying idea — *log which candidates the ensemble consistently rejects, not just which one it picked* — is adoptable as pure bookkeeping, no training required:

**Proposal:** when both models' logprobs (already extracted per-token by `extract_verdict_confidence()` in `src/llm_client.py`) put near-zero mass on a given `RESOLVED_TO_CANDIDATE_N` across the small closed verdict vocabulary for a record, log those candidate indices alongside the decision (a `rejected_candidates` field, cheap to add to the artifact dict already built in `validate_record()`). Two concrete uses, both symbolic and auditable rather than statistical:

1. **Stage 2b re-ranking feedback.** If a candidate is consistently rejected by Stage 3 across multiple notes it appears in, that's evidence worth surfacing back to whoever curates the vocabulary/synonym tables — not an automated write, a flagged-for-review list. Directly serves the "high-confidence labels dynamically stored back... to enrich future context" language in Objective 3, at the rejection end rather than only the acceptance end, which the current design doesn't do at all.
2. **A second, independent input to the citation guard.** If a model cites a `rule_id` in support of a candidate its own logprobs simultaneously rank as near-zero-likelihood, that's an internal inconsistency worth surfacing to a human reviewer even when `verify_citations()` passes — the citation existing doesn't mean it was used coherently.

Table 3 in the paper (false negative rate 0.02-0.3% across datasets) is worth citing as precedent that this kind of low-confidence-set bookkeeping is reliably clean, not noisy — the risk of over-trusting it is low.

## 5. What not to adopt now, and why

| MoLLIA mechanism | Verdict | Reason |
|---|---|---|
| Iterative AL retraining loop (Algorithm 1) | **Defer to Stage 4/5** | Requires a retrained downstream classifier this pipeline doesn't have. Building one now to unlock the loop is solving a problem Objective 3 hasn't reached — HITL routing and KG3 write-back come first per the existing roadmap in `docs/Proposal_Alignment_Review.md` §4. |
| Negative learning loss (`L_neg`, Eq. 7) | **Not applicable yet** | Same reason — it's a training-time penalty against a classifier that doesn't exist. The *bookkeeping* half (§4.3) is adopted; the *gradient* half is not, because there's nothing to apply a gradient to. |
| Pseudo-labeling threshold `σ=0.9` for unlabeled-pool expansion | **Not applicable** | This expands MoLAM's *own* training set using its own high-confidence predictions on unlabeled data — a self-training loop for the annotator itself. Stage 3 isn't trained at all (it's two fixed local LLMs); there's no analogous "MoLAM training set" to expand. If MoLLM-Cal (§4.1) is ever self-trained on its own high-confidence outputs, this idea becomes relevant again — flag as a future extension, not now, since it would need its own calibration-of-the-calibrator safeguards first. |
| T-fold self-consistency per model | **Defer, hardware-gated** | Real signal-quality upside (consistency scores are half of MoLAM's input), but collides with the T4 VRAM/KV-cache budget documented in `scripts/start_vllm.sh` and would multiply the already-measured 5.32s/record runtime. If revisited, scope it to T=2-3 on the LOW-tier resolution-mode subset only (where the signal matters most and volume is lower), not universally — and measure the VRAM headroom empirically before committing, since `--gpu-memory-utilization 0.40/0.55` was sized for T=1. |
| 5-member LLM ensemble | **Not applicable** | `docs/MoLLM_Stage3_Retrieval_Design.md`'s header already documents why the ensemble is exactly two members with deliberately non-correlated base architectures (Mistral vs. Llama-3) on a single T4 — a third member is a VRAM problem before it's a design question, and the diversity argument the paper uses to justify 5 members is already satisfied by architectural independence, not member count. |

## 6. Proposal-alignment check

Re-reading Objective 2, Objective 3, and the Methodology §3 "Ensemble Policy" paragraph against this proposal: nothing here expands scope. The proposal's own words — *"A voting mechanism then evaluates the confidence of the proposed labels. If the ensemble's consensus falls below a predefined confidence threshold... routed to a human... High confidence labels are automatically accepted"* — describes exactly `combine()` + `route()`'s current job. §4.1 is a refinement of *how the threshold comparison is computed*, not a new mechanism, and it's justified by evidence this project already collected (`Stage3_Open_Issues.md` Issue 4) rather than by the paper alone. §4.2 and §4.3 add auditable, symbolic signals consistent with the "deterministic, white-box, traceable" language throughout the Legal/Ethical section — if anything, a trained calibrator over already-logged, inspectable features is a more defensible instantiation of "explainable" than the current unexplained constants `0.85`/`0.60`, which `Stage3_Open_Issues.md` itself already calls "currently unjustifiable numbers."

One thing worth flagging explicitly for the dissertation rather than treating as implicit: MoLLIA is cited in the proposal's Background Research as prior work motivating the Mixture-of-LLMs framing in general terms, not as an architecture Objective 2/3 commit to replicating exactly. This document is the record of having checked the literal mechanism against what's buildable and useful here, and adopting the parts that survive that check — which is the kind of explicit reconciliation `docs/Proposal_Alignment_Review.md` §3.1 already recommended doing for the Objective 4 dataset pivot; the same discipline applies here.

## 7. Build sequence

This slots into the sequence `docs/Stage3_Open_Issues.md` already established ("fix retrieval, then calibrate") rather than replacing it — §4.1-4.3 above **are** the calibration step that document deferred.

1. **Let the batch run currently in flight finish** (`scripts/run_stage3_batch.py`, restarted after the salvage-regex and resumability fixes). Its resolution-mode, agreeing, gradable decisions are MoLLM-Cal's only source of labeled training data — there is no substitute dataset to start on early.
2. **Extend `evaluation/cal_eval.py`'s feature extraction** to also emit the raw feature vector (not just the ECE/threshold-sweep report it currently produces) per gradable decision, plus the `d_anno` join against `normalized_entities` (§4.2). This is additive to existing code, not a rewrite of it.
3. **Fit MoLLM-Cal** (logistic regression first) once the gradable sample clears a defensible floor — n=6 (the last measured run) is not that floor; treat this the same way `Stage3_Open_Issues.md` already treats the raw threshold fit, i.e. explicitly don't trust it below whatever sample size `docs/Evaluation_Criteria.md`'s validation-slice design calls for.
4. **Wire MoLLM-Cal's output into `route()`** as a drop-in replacement for the two threshold comparisons at lines 620-626, behind the three unchanged safety-rule short-circuits.
5. **Add `rejected_candidates` bookkeeping** (§4.3) to the artifact dict in `validate_record()` and to `mollm_decisions`' schema — additive column, no migration risk to existing rows (DuckDB `ALTER TABLE ADD COLUMN` or a fresh column in the existing `CREATE TABLE IF NOT EXISTS`).
6. **Re-run `cal_eval.py`'s guided-only ECE report** against MoLLM-Cal's output vs. the old `composite_confidence`, on the same gradable set, as the direct before/after comparison for the dissertation — this is the paper's own Table 2 comparison (hand-combined vs. trained aggregator), reproduced on this project's own task.

## 8. Honest limitations to state alongside this

- **Sample size risk cuts both ways.** Too few gradable examples and MoLLM-Cal overfits or learns nothing; this document does not propose a specific floor because `docs/Evaluation_Criteria.md`'s validation-slice sizing is the right place to set one, not this document.
- **The gradable subset is a biased sample of Stage 3's total output.** `cal_eval.py` already documents that only resolution-mode, agreeing decisions are gradable — contradiction-mode and disagreement cases never enter MoLLM-Cal's training set, so its calibration is only proven for the subset it was fit on. This mirrors a limitation already stated in `docs/Stage3_Open_Issues.md` Issue 4 and is not new to this proposal, but is worth restating: MoLLM-Cal does not close the gap on contradiction-mode confidence, which stays ungraded until the periodic human re-audit sample `docs/Evaluation_Criteria.md` names materializes.
- **A trained calibrator is one more thing to keep auditable.** Logistic regression coefficients are inspectable in a way that satisfies the "white-box" pitch; if the sample size ever justifies moving to XGBoost, that trade-off (accuracy vs. the same explainability standard applied to every other component) should be made explicitly, not by default.

## 9. Addendum (2026-08-11) — grounding is an input, not a gate; refining the no-evidence regime

Follow-up to a design discussion after §1-8 above. The position: Objective 2's KG grounding is meant to *help* the LLM ensemble decide and to solve cold start — it is not supposed to be a hard prerequisite for trusting a verdict. When no guideline rule matches, the ensemble should still vote, and how much to trust that vote should be settled empirically (measure each model's ECE in that regime, set a threshold) rather than assumed to be untrustworthy by default. Checked against the code below; mostly already true architecturally, with one real gap.

### 9.1 Already true, no change needed
- Channel C (SNOMED ontology context — FSN, semantic tag, immediate parents) is retrieved for **every** record regardless of whether a guideline rule matches (`src/retrieval.py`, `docs/MoLLM_Stage3_Retrieval_Design.md` §5.6). Guideline evidence (Channels A/B/D) is a bonus layer on top, not the base grounding — the ~91.5% of entities with no guideline evidence still get ontological grounding, never zero context.
- Resolution mode already runs both models regardless of evidence presence — `build_prompt()`'s mode selection depends only on `confidence_tier_in` + candidate count (`src/mollm_ensemble.py:245-249`), not on whether any rule was retrieved. The "voting mode when nothing matches" behavior described already exists; it isn't a new mechanism to build.
- `confidence_tier_in` (HIGH/LOW) never depends on guideline-evidence presence — only Stage 2 signals do. Lack of a KG hit doesn't itself downgrade an entity's tier.
- This reading matches Objective 2's actual wording — "retrieves factual data from the KG to **guide** the LLM" — not "gates the LLM's output on evidence being present."

### 9.2 The real gap: the system prompt currently forbids the reasoning this design needs
`SYSTEM_PROMPT` (`src/mollm_ensemble.py:88-123`) states plainly: *"Judge ONLY what you are shown. Do not use outside clinical knowledge as evidence for a verdict."* That instruction is unconditional — it applies identically whether or not guideline evidence exists. As written, it tells the model not to lean on its own clinical expertise even in the no-evidence case, which is the opposite of "small models, real context expertise, provenance is enough." Right now the model is being told to suppress the exact capability this design wants it to use.

**Proposed fix — narrow the rule to what it actually protects against, and scope it to the labeling task, not clinical decision-making.** The anti-hallucination concern is fabricated citations (inventing a `rule_id`, quoting text never shown), not domain knowledge per se — `verify_citations()` already checks for that independently. And per §9.6 below, the task this reasoning serves is *"is this the correct concept label for this text span,"* not *"is this patient's care correct"* — so the replacement instruction should say that explicitly rather than invite general clinical reasoning:

> When no guideline evidence is retrieved, you may use your knowledge of medical terminology and clinical concepts to judge whether the candidate concept is the correct label for the entity shown, given its context. This is a labeling judgment — whether this text correctly refers to this concept — not a judgment about whether the patient's care is clinically appropriate. You must not attribute this judgment to a guideline, and you must not cite a `rule_id` you were not given.

This keeps the fabrication guard fully intact, unlocks the terminology expertise the no-evidence regime needs, and keeps the model's task the same shape as everywhere else in this pipeline: entity-to-concept correctness, not care-quality assessment.

### 9.3 Calibrate the two regimes separately, don't pool them
Extends §4.1's MoLLM-Cal proposal: stratify by `has_guideline_evidence ∈ {True, False}` before fitting or reporting ECE, the same way `evaluation/cal_eval.py` already splits by `decoding_purity` (guided vs. unguided decoding — a precedent for exactly this kind of regime split already existing in this codebase). Report both ECE curves separately, not blended — pooling them risks a calibrator dominated by whichever regime has more examples (almost certainly the no-evidence regime, since it's ~91.5% of records), which would silently under-calibrate the rarer with-evidence subset.

**One reason to be more careful in the no-evidence regime, not less.** Of `route()`'s three hard safety rules, "citation verification failed" is structurally inert when zero rules were retrieved — `citation_verified` is vacuously true, nothing exists to fabricate against. So the no-evidence regime runs on two safety nets (model agreement, calibrated threshold) instead of three, while `docs/Stage3_Open_Issues.md` Issue 3 already showed both models agreeing confidently on a wrong answer (composite 0.916) even *with* candidates and the citation guard active. The regime with fewer safety nets should get the higher evidentiary bar for its threshold — a larger required calibration sample before it's trusted — even though the end goal (stop reflexively routing every no-evidence record to HITL) is correct.

**Don't loosen `route()`'s hard rules directly.** `INSUFFICIENT_EVIDENCE`/`CONTRADICTED` forcing HITL (lines 609-618) should stay exactly as strict as it is. The fix belongs at the prompt layer (§9.2): once the model is allowed to reason its way to `SUPPORTED` from context instead of defaulting to `INSUFFICIENT_EVIDENCE` out of instructed caution, that hard rule naturally fires less often — because the thing feeding it stops over-triggering, not because the gate was loosened. `docs/Stage3_Open_Issues.md`'s Issue-1 finding (10/10 records routed to HITL when zero rules were retrieved) is consistent with this diagnosis: a prompt anchoring the model toward caution, not a policy that no-evidence records are inherently untrustworthy.

### 9.4 Data repurposing and KG hit-rate growth — which KG, precisely
Two different growth mechanisms get conflated if this isn't stated precisely:

- **KG1's guideline-rule coverage is curation-bound, not repurposing-bound.** `docs/MoLLM_Stage3_Retrieval_Design.md` §2.2b already measured this exactly: 41 high-frequency guideline nodes (`Physical examination` 645 gold annotations, `Hypertension` 551, `Clinical evaluation` 345, ...) carry zero attached rules — worth +3.25pp coverage — and the document calls this "curation work, not code." No volume of repurposed classification data adds a new guideline rule; only a human curator attaching one does. Objective 4's KGE pipeline doesn't touch KG1.
- **What Objective 4's repurposing actually grows: KG3 (patient-instance history) and Stage 2b's candidate/synonym coverage.** `docs/Proposal_Alignment_Review.md` §6 already settled this — triplets into KG3 first, embeddings as a derived re-ranking layer over accumulated instances, growing as more notes are processed.
- **Concrete link between the two, buildable now:** turn the curation gap into a live queue instead of a one-time manual pass. When a record resolves `SUPPORTED` under the relaxed §9.2 prompt at high calibrated confidence with no guideline evidence, *and* that same concept recurs across many notes, that's a ranked, continuously-refreshed candidate list for "which guideline node most needs a rule attached next" — the same population §2.2b found once by inspection, now surfaced as a byproduct of normal pipeline operation. This extends §4.3's negative-candidate bookkeeping in the opposite direction (flagging confident, evidence-starved *hits*, not rejected candidates), and gives Objective 4 a direct, measurable role in Objective 2's coverage number instead of the two objectives running in parallel with no connection between them.

### 9.5 The purpose of choosing clinically fine-tuned models, made explicit

Worth stating plainly, because §9.2's prompt fix is answering it: BioMistral-7B and OpenBioLLM-8B were deliberately chosen for their clinical fine-tuning (`docs/MoLLM_Stage3_Retrieval_Design.md`'s header documents the MedGemma→BioMistral swap specifically to preserve non-correlated clinically-tuned base families). Under the current unconditional "do not use outside clinical knowledge" instruction, that trained expertise is being paid for in compute and never used in the verdict. That's not a wording nitpick — it's the system suppressing the exact property the models were selected for, and (per §9.6) what it's suppressed *for* is narrower and safer than general clinical reasoning: it's the model's knowledge of medical terminology and concept relationships, applied to a labeling task.

**This isn't a gap that closes as the KG grows — it's permanent by construction.** The guideline corpus is 10 documents covering a fixed set of high-acuity conditions (AKI, sepsis, HF, COPD, ACS, CAP, triage). A discharge summary spans the full range of clinical medicine. No amount of curation (§9.4) makes a finite, curated guideline corpus the same size as general clinical/terminology knowledge — the two are structurally different sizes, permanently. So the model's own trained knowledge is not a stand-in for "until coverage improves"; it's the permanent second half of the architecture, required for as long as guidelines remain curated rather than exhaustive (which is the entire point of curating them).

**The current prompt already half-relies on this without admitting it.** "Return SUPPORTED if the mapping is ontologically sound" (`src/mollm_ensemble.py:100`) cannot be executed as a mechanical check — judging whether a SNOMED concept plausibly labels an entity in context requires terminology/domain understanding, not lookup. The model is very likely already drawing on its trained knowledge to answer that instruction; the prompt just doesn't label it as such, so it happens unlabeled rather than auditably.

**Proposed addition: an explicit, recorded grounding basis, not a blurred one.** Add a field to the decision artifact — `grounding_basis ∈ {guideline_rule, ontology_only, model_terminology_knowledge}` — set per verdict based on what the model actually leaned on (guideline evidence present and cited; no guideline evidence but the verdict rests on Channel C's structured ontology facts alone; no guideline evidence and the verdict required the model's own terminology/domain knowledge beyond what Channel C states). This is what keeps the "white box, deterministic, traceable" claim intact *while* using what the models were chosen for — a reviewer (or the dissertation) can see exactly how much of the auto-validated set rests on checkable facts versus model expertise, instead of that distinction disappearing into one undifferentiated confidence number.

**This sharpens §9.3's stratification from two-way to three-way.** `model_terminology_knowledge` is the least checkable of the three tiers — no citation to verify, no structured ontology fact to point at, and (per §9.3) the citation safety rule is already inert here. It should carry the highest evidentiary bar of the three for MoLLM-Cal's threshold, not the same bar as `ontology_only`, which at least rests on structured, retrievable facts even without a guideline rule behind it.

### 9.6 Scope boundary: this is a labeling validator, not a clinical decision support system

Explicit correction to how §9.2-9.5 above should be read, made after a design discussion: everywhere those sections say "clinical judgment" or "clinical reasoning," the intended and correct scope is narrower — **the task is entity-to-concept label correctness ("is this SNOMED/OMOP concept the right label for this text span"), not clinical decision-making ("is this the right diagnosis," "is this treatment appropriate," "did this care follow guidelines").** This isn't a stylistic preference; it's what the project proposal actually commits to. The Aim section states the goal as *"develop and evaluate a semi-automatic **data labelling framework**"* — every objective is phrased in terms of labels, annotation, and NER dataset construction, never diagnosis, treatment, or care-quality assessment. Building anything that reads as clinical decision support would itself be a proposal-alignment problem, the same category of issue `docs/Proposal_Alignment_Review.md` was written to catch.

**What this changes, concretely:**

- The `model_terminology_knowledge` grounding tier (§9.5) is scoped to *"does this concept correctly name what the text refers to,"* using the model's knowledge of medical terminology and concept relationships — not general clinical reasoning about the patient's presentation or management. §9.2's prompt wording above has been written to say this directly rather than leave it implicit.
- The existing `CONTRADICTED` verdict (`src/mollm_ensemble.py`, contradiction mode) should be read the same way even though its current framing risks sounding otherwise: it's asking whether the *guideline evidence retrieved about this concept* is inconsistent with *this concept being the correct label* for the entity in context — using guideline content as validating evidence for a labeling decision, the same way a usage note in a terminology reference would be used to sanity-check a translation choice. It is not asking "did this patient's care follow the guideline." The existing code comment at `route()`'s `guideline_contradiction` branch ("a clinical finding for a human, not something to auto-resolve") is worth revisiting for the same reason — not because the routing behavior is wrong, but because "clinical finding" describes a care-quality judgment this component was never meant to make. A more precise phrasing would be closer to "a flagged label/evidence inconsistency for a human to adjudicate."
- This also narrows, favorably, the risk surface raised in §9.3. A wrong `model_terminology_knowledge` verdict produces a wrong label on a text span — a data-quality error catchable by downstream review, gold-set evaluation, or a human annotator — not a clinical recommendation a clinician could act on. The system was never going to be evaluated as, or deployed as, a source of care advice, and nothing in §9.1-9.5 should be read as expanding it toward that role.

## 10. Retrieval design — relations are extracted, linked, and completely unused by `retrieve()`

Raised in a follow-up design discussion: is KG1 retrieval over-reliant on SNOMED codes, and under-using node `@type` and GLiNER-relex relations? Checked directly against `src/retrieval.py` and `src/extraction.py`. One part of this turned out to already be well-handled; one part is a real, clean, currently-unaddressed gap.

### 10.1 Node `@type` is already used — correction to the framing, not a new finding
`retrieval.py` (`TYPE_COMPATIBILITY`, `type_agreement()`, `combined_type_agreement()`, lines ~100-473) already checks the GLiNER label *and* the matched concept's OMOP domain against each guideline node's `@type`, independently, and applies a `TYPE_MISMATCH_PENALTY = 0.85` multiplier to `match_confidence` on disagreement — across Channels A, B, and D, plus a ranking tiebreaker in `rank_and_cap()` (below `match_confidence` and `citation_type`, above predicate affinity). This is deliberately a **soft multiplier, not a hard filter**, and the code documents why: the corpus's own `@type` field is internally inconsistent (41+ SNOMED codes carry conflicting `@type` across nodes — "Statins" tagged both `Finding` and `Medication`), so a hard gate would suppress correct evidence roughly as often as wrong evidence. Type-awareness is already load-bearing here; it isn't an unused signal.

### 10.2 Relations are extracted, offset-linked, confidence-floored — and invisible to retrieval
`extraction.py` runs a real GLiNER-relex pass, links each relation's endpoints to `extracted_entities` by character-offset overlap (≥50%, `MIN_ENDPOINT_OVERLAP`), and stores `head_entity_id`/`tail_entity_id`/`relation_label`/`relation_confidence` (floored at 0.7) in `extracted_relations`. Those relations are surfaced to the LLM in the Stage 3 prompt as a display-only block (`docs/MoLLM_Stage3_Retrieval_Design.md` §6, block 5 — "RELATIONS ... each annotated with its `entity_link_status`"). But `GroundingRetriever.retrieve()` (`src/retrieval.py:1082-1176`) never reads `record.get("relations")` — the four channels (A/B/C/D) all operate on the single entity in isolation. The model sees a relation exists; the KG query that assembles its evidence does not use it.

### 10.3 Proposed Channel E — relation-aware structured match
For an entity X with a linked relation R to entity Y, query KG1 for a guideline edge connecting a node compatible with X to a node compatible with Y through a predicate compatible with R — reusing `name_agreement_guard()` and `combined_type_agreement()` exactly as they run today, applied to both endpoints of a relation rather than one entity alone. A guideline rule that names both the medication and the condition it treats is stronger, more specific evidence than either entity matched independently, and this is a genuinely different traversal than Channel B's upward-only `IS_A` walk — sideways through the KG's predicate structure rather than up the hierarchy. It could also reach entities Channel A/B/D currently miss entirely: if X alone has no code/name match but its relation partner Y does, a joint query surfaces evidence for X indirectly through Y.

**The actual blocker: a label-mapping table doesn't exist yet, and building it is the real task, not the query logic.** GLiNER-relex's relation vocabulary is deliberately small and closed — `treated with`, `indicates`, `causes`, `located in`, `measured by` (`extraction.py:97-103`) — against KG1's 49 canonicalized guideline predicates (`REQUIRES_MEDICATION`, `INDICATES`, `TRIGGERS_SEVERITY`, ...). No mapping between the two exists. Some pairs look direct (`indicates` ↔ `INDICATES`), others need direction handled explicitly (`treated with` runs Medication→Condition; the guideline-side analog plausibly runs Condition→Medication). This mapping should be built and spot-checked by hand against a sample before being trusted, the same way every other threshold and guard band in `docs/MoLLM_Stage3_Retrieval_Design.md` was calibrated by measurement rather than assumption.

**Measure reach before claiming a coverage number.** Channel E only fires for entities with a `resolved` `entity_link_status` (overlap ≥ 0.5) to another entity — nobody has measured what fraction of gold entities that actually is. Given `docs/MoLLM_Stage3_Retrieval_Design.md` §2.1 measured Channel B's contribution before relying on it (+3.61pp guarded, not assumed), Channel E's reach should get the same treatment: run `extracted_relations` coverage against the gold set first, then estimate Channel E's plausible lift, rather than presenting it as a win before it's measured.
