# Rules-LLM Triplets Review — Comparison Against the MedCAT-Based Corpus

Reviewed 2026-08-07. Scope: `data/rules-llm/` — 94 triplet files generated by calling an LLM directly via API over the same source guideline chunks used for `data/local_triplets_db2_v6/` (the MedCAT-pipeline corpus reviewed in `Guideline_Triplets_KG_Review.md`). Same method as before: parsed all 94 files programmatically, cross-checked citations against the raw source chunks in `data/triplets-rules-backup-data/local_chunks_db2_v6/`, spot-checked ICD10 codes against known-correct mappings.

**Headline: this is the better corpus on the dimensions that matter most for grounding, and should likely be the primary source for `init_memgraph_guidelines.py`** — but it has its own, different set of problems, and neither corpus should be ingested as-is.

---

## 1. Head-to-Head

| Dimension | `local_triplets_db2_v6` (MedCAT pipeline) | `data/rules-llm` (LLM via API) |
|---|---|---|
| Files / source docs | 76 files, 10 guideline docs | 94 files (covers ~all chunks, including front-matter/methodology sections the MedCAT pipeline skipped) |
| Total nodes / rules | 1,969 nodes / 1,203 rules | 972 nodes / 706 rules |
| SNOMED grounded | **50.5%** (974/1,969 = `"N/A"`) | **96.5%** (938/972 real; 34 missing the key, 0 explicit `"N/A"`) |
| ICD10 populated | **0%** (all `"N/A"`) | **71.5%** (695/972) |
| Within-file duplicate nodes | **63%** of nodes redundant (73/76 files affected) | **0%** — no duplicate node names found in any file |
| Rule referential integrity | **100%** — 0 dangling targets / 1,203 | **85.6%** — 102 of 706 rules (14.4%) point to a `target` UUID that doesn't exist in the file |
| Citation verbatim-containment (vs. source chunk) | 47% high-containment, 27% low/pointer-style | **71%** high-containment, 5.6% low (and the low ones are mostly figure/table content that has no clean linear text to quote, a more defensible failure mode) |
| Predicate vocabulary | 30+ distinct predicates, rich but inconsistent (near-duplicates like `NOT_RECOMMENDED_FOR` vs `SUGGESTS NOT USING`) | Only 5: `INDICATES`, `REQUIRES_INTERVENTION`, `TRIGGERS_SEVERITY`, `REQUIRES_MEDICATION`, `TRIGGERS_INTERVENTION` — cleaner, but loses negative/contraindication and evidence-quality relations the other corpus captured (`NOT_RECOMMENDED_FOR`, `POTENTIAL_BENEFIT`, `IS_LIMITATION`, etc.) |
| Schema consistency | Uniform `{"@context", "@graph"}` wrapper throughout | **Mixed**: 85 files are bare JSON arrays, 9 are `{"@context","@graph","_db2_status","chunk_id","section_title"}` dicts. `snomed`/`icd10` field values are **also inconsistently typed** — usually a string (e.g. `"703348002"`), but 154 nodes (16%) have `snomed` as a `{"code","display"}` dict instead, and 128 (13%) have `icd10` as a dict, across 18/94 files. 2 nodes even have `snomed` as a list. |

## 2. What's Genuinely Better Here

- **Grounding rate is night and day**: 96.5% vs 50.5%. Spot-checked several well-known mappings and they hold up — `Community-Acquired Pneumonia` → SNOMED `703348002` / ICD10 `J18.9` (correct), `COPD` → `13645005` / `J44.9` (correct), `History of Childhood Asthma` → `Z87.01` "Personal history of asthma" (correct and appropriately specific). This alone would resolve most of §3.1 in the earlier review if this corpus is used instead of (or merged with priority over) `local_triplets_db2_v6`.
- **No node duplication.** The LLM-based extraction appears to consolidate mentions of the same concept into one node rather than emitting a new node per statement, which was the single biggest structural problem in the other corpus (§3.2 there). This is a real methodological advantage worth calling out in the dissertation — it suggests prompting the LLM with "extract one canonical node per distinct concept" (or similar) works, versus MedCAT's mechanical per-mention injection.
- **Citations are substantially more verifiable** (71% vs 47% high-containment), and the low-containment cases here are legitimately hard content (a risk-score nomogram figure, "Figure 1. Ottawa Heart Failure Risk Scale...") rather than the other corpus's vague meta-pointers ("Section 3, Levy et al study description"). This matters directly for Stage 3's planned `citation_verified` check.
- **Explicit empty-result handling.** The 9 dict-shaped files all carry `"_db2_status": "empty"` with an empty `@graph` — meaning the pipeline correctly identified that front-matter/methodology/evidentiary-table chunks had nothing worth extracting and said so explicitly, rather than silently omitting the file or crashing. Good practice, worth preserving as a pattern.

## 3. What's Worse or New Here

### 3.1 Referential integrity has regressed — 14.4% of rules point nowhere
Concrete example: two separate rules (`"High Risk for Serious Adverse Event per OHFRS"` and `"High Risk for 30-day Adverse Event per STRATIFY tool"`) both target the same UUID, which never appears as a node anywhere in that file. This looks like the LLM describing a consequence/target concept in the rule's `rationale` text without also emitting it as its own top-level node — a classic LLM structured-output failure mode (referencing something it "meant to" generate but didn't). **This needs a validation pass before ingestion**: for every `target` UUID, confirm a matching node exists; if not, either synthesize a minimal stub node from context or drop the rule and log it for review. Given the other corpus has 0% dangling targets, this is a specific regression worth fixing rather than accepting.

### 3.2 Inconsistent field typing for `snomed`/`icd10` — will silently break a naive loader
Most nodes store `snomed`/`icd10` as a plain code string (`"snomed": "703348002"`), but **154 nodes (16%) store `snomed` as `{"code": "...", "display": "..."}`, and 128 (13%) store `icd10` the same way**, across 18 of the 94 files. Example, same file, two different shapes: `'heart failure' -> snomed: '67533008'` (string) vs `'sepsis' -> snomed: {'code': '186314008', 'display': 'Urosepsis'}` (dict). Any ingestion script that assumes `node["snomed"]` is always a string will either crash or silently write a Python dict's string representation into Memgraph as if it were a code. **This is a higher-priority fix than the dangling-targets issue** because it fails silently rather than loudly — normalize with something like `code = v["code"] if isinstance(v, dict) else v` before writing anything to the graph.

### 3.3 Mixed top-level schema (list vs. dict-wrapped)
85 files are bare `[...]` arrays of nodes; 9 are `{"@context", "@graph", "_db2_status", ...}` objects (the empty-result cases). A loader needs to branch on `isinstance(data, list)` — trivial to handle, but undocumented and will break a naive `json.load()["@graph"]` pattern on 90% of the files.

### 3.4 ICD10 accuracy needs spot-checking, not blanket trust
Most spot-checked codes were correct, but not all. One from the KDIGO AKI file: `"Acute Kidney Injury (AKI) Stage 1"` was mapped to ICD10 `N17.0` — "Acute kidney failure with tubular necrosis." That's a specific *etiological subtype* of AKI, not a KDIGO *severity stage* — ICD-10-CM doesn't actually have stage-specific codes for KDIGO AKI staging, so this particular code looks like a plausible-but-wrong LLM guess rather than a real mapping (worth verifying against an authoritative SNOMED→ICD10 crosswalk rather than trusting the LLM's assertion, exactly the failure mode ICD10 crosswalks via OMOP's `Maps to` relationship — as your `backfill_guideline_grounding.py` does — are meant to avoid, since that path derives the code from a maintained mapping table rather than an LLM guessing it). Recommend cross-validating a sample of this corpus's `icd10` values against the OMOP `Maps to` relationship (same mechanism already built for the backfill script) and flagging mismatches rather than trusting either source blindly.

### 3.5 Predicate vocabulary lost some real information
Collapsing from 30+ predicates down to 5 loses categories like `NOT_RECOMMENDED_FOR`, `POTENTIAL_BENEFIT`, and `IS_LIMITATION` that the MedCAT/triplet-extraction corpus captured — these carry real clinical-safety signal (e.g., "don't give diuretics early without confirming volume overload" is a *contraindication*, and losing that distinction and folding it into a generic `INDICATES` or omitting it changes what Stage 3 can reason about). Worth checking whether this corpus's *rationale* text still captures that nuance in prose even where the predicate doesn't — if so, a light post-processing pass could re-derive the missing predicate types from rationale text rather than needing to redo the extraction.

---

## 4. Recommendation

Neither corpus should be ingested into Memgraph as-is. Given the comparison, the practical path is likely:

1. **Use `rules-llm` as the primary source** for `init_memgraph_guidelines.py` — it starts from a much stronger grounding position (96.5% vs 50.5%) and doesn't have the node-duplication problem, which was the single largest structural blocker identified in the other corpus.
2. **Before ingesting it**, run three mechanical passes: (a) normalize the list-vs-dict top-level schema, (b) normalize `snomed`/`icd10` field values to always be a plain code string, (c) validate every rule's `target` against the file's own node `@id`s and drop/flag orphaned rules rather than silently creating dangling edges in Memgraph.
3. **Spot-check a larger sample of `icd10` values** against the OMOP `Maps to` crosswalk before trusting them wholesale — the one clear miss found (AKI Stage 1 → N17.0) suggests this isn't perfectly reliable, and ICD10 crosswalking is exactly the kind of task better delegated to a deterministic OMOP lookup than an LLM's recall.
4. **Consider `local_triplets_db2_v6` as a supplementary source for predicate richness**, not the primary node source — its `NOT_RECOMMENDED_FOR`/`POTENTIAL_BENEFIT`/`IS_LIMITATION`-style relations capture safety-relevant nuance `rules-llm` currently doesn't, and could be merged in for the subset of concepts where both corpora describe the same SNOMED-coded node.
5. Either way, `scripts/init_memgraph_guidelines.py` needs to `MERGE` by `snomed` code (not `@id`) regardless of which source feeds it — this recommendation from the earlier review still applies, it's just less urgent for `rules-llm` specifically since that corpus doesn't already contain within-file duplicates the way the other one does.
